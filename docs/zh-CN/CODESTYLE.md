# 编码规范与工程标准 (Code Style and Engineering Standards)

本文档定义了 Lemon Agent 的强制编码标准。所有生产代码、测试、文档、配置示例、提交信息、日志、错误信息以及对开发者可见的文本都必须遵守这些规则。

## 1. 语言

- 代码库中统一使用英语。
- 标识符、注释、文档、日志消息、错误消息、测试名称、配置键和示例一律使用英语。
- 不要在源文件或开发者文档中混用语言。
- 优先使用清晰直白的措辞，避免缩写或内部行话。

## 2. 生产级代码

- 编写完整、可投产的实现，而不是原型或占位符。
- 除非附有问题引用和具体理由，否则不得提交 `TODO`、`FIXME`、桩实现、模拟返回值、静默回退或注释掉的代码。
- 显式处理预期的失败，并保留有用的诊断上下文。
- 在生产路径中避免 `unwrap`、`expect`、`panic!` 和不可达假设。仅在测试中为了让测试更清晰时才使用它们。
- 在系统边界校验所有外部输入。
- 将文件系统访问、子进程执行、网络调用、数据库操作和 LLM 响应都视为可能失败的操作。
- 对可能阻塞或消耗无界资源的操作施加超时和资源限制。
- 将安全检查保留在 Rust 内核中，绝不以脚本或提示词作为安全边界。

## 3. 项目结构

- 按职责和领域组织代码，而不是仅按便捷性或文件大小。
- 保持依赖方向明确：高层编排可以依赖稳定接口，而核心安全与持久化模块不得依赖高层策略代码。
- 使用小型的、内聚的模块，并保持清晰的公共 API。
- 默认隐藏实现细节；只暴露其他模块真正需要的内容。
- 将纯领域逻辑与 I/O、持久化、网络和进程执行分离。
- 优先使用组合和 trait，而不是全局状态或紧耦合的具体实现。
- 将共享测试工具放在专门的测试支持模块中，而不是生产模块中。
- 当存在精确的领域名称时，不要创建通用的 `utils`、`helpers` 或 `common` 模块。

## 4. 可读性与命名

- 选择无需注释就能传达意图的名称。
- 遵循 Rust 命名约定：
  - 函数、方法、模块、变量和文件名使用 `snake_case`。
  - 结构体、枚举、trait 和枚举变体使用 `PascalCase`。
  - 常量和静态量使用 `SCREAMING_SNAKE_CASE`。
- 布尔值命名为谓词形式，例如 `is_valid`、`has_capacity`、`should_retry`。
- 当可能存在歧义时在名称中包含单位，例如 `timeout_secs`、`size_bytes`、`timestamp_ms`。
- 避免无法解释的缩写，以及在小局部作用域之外使用单字母名称。
- 保持函数职责单一。当函数混入策略、I/O、转换和错误处理时，应进行提取。
- 优先使用提前返回，而不是深层嵌套的控制流。
- 先追求清晰，再考虑性能；只有存在证据或明确记录的约束时才做性能优化。

## 5. 注释与文档

- 只有当注释提供了代码本身无法清晰表达的必要的技术背景时才编写注释。
- 优先解释某个约束、不变量、变通方案或安全决策存在的原因。不要叙述下一行代码做了什么。
- 保持注释简洁、精确且有技术价值。
- 删除过时、冗余、臆测性、装饰性和闲聊式的注释。
- 不要用注释来弥补不清晰的命名或糟糕的结构；改进代码本身。
- 当公共 API 的契约、不变量、失败模式、安全影响或副作用不明显时，为其编写文档。
- 对于 unsafe 代码，在 unsafe 块旁边立即记录每条必要的安全不变量。
- 对于不明显的变通方案，在可用时说明根本原因和稳定引用。

## 6. 可调试性与可观测性

- 让每个重要操作都可以在不挂接调试器的情况下被诊断。
- 使用带稳定字段名的结构化日志，而不是仅靠插值文本。
- 包含相关关联字段，如 `continuity_id`、`step_num`、`event_type`、`tool_name` 和耗时。
- 记录状态转换、重试、超时、可恢复失败、预算耗尽、进化尝试和回滚结果。
- 一致地使用日志级别：
  - `error`：当前操作无法完成，或数据完整性可能受损。
  - `warn`：操作已恢复、降级或需要关注。
  - `info`：有意义的生命周期和状态变化。
  - `debug`：开发或事故分析时有用的诊断细节。
  - `trace`：正常生产运行中禁用的高量内部细节。
- 绝不记录 API 密钥、授权头、能力机密、原始凭据或未经脱敏的敏感内容。
- 保留错误来源，并在每个抽象边界添加上下文。
- 优先使用调用方可以检查的类型化错误，而不是匹配任意错误字符串。
- 确保失败能标识出操作、相关的安全标识符和有价值的成因。

## 7. Rust 专项规则

- 使用项目清单选定的稳定版 Rust 和版本。
- 遵循惯用的所有权和借用；避免仅为平息借用检查器错误而克隆。
- 优先使用显式的领域类型，而不是松散相关的原始值。
- 对封闭状态集合使用枚举，并使非法状态难以表示。
- 当静默忽略返回值很可能导致 bug 时，用 `#[must_use]` 标记返回值。
- 保持异步临界区短小，绝不在 `.await` 期间持有同步锁。
- 除非无界设计有充分理由，否则使用有界通道和有界并发。
- 避免 `unsafe`。如果不可避免，将其隔离在安全 API 之后并测试其不变量。
- 功能开关保持可叠加、有文档，并在支持时由 CI 覆盖。

## 8. 错误处理与恢复

- 对可能失败的操作使用 `Result`，并有意识地传播错误。
- 在适当的领域边界定义错误；不要不必要地暴露底层实现细节。
- 添加上下文时不要丢弃原始错误链。
- 在行为不同的地方区分可重试、可恢复、终止性、校验、授权和预算错误。
- 重试必须有界，并对外部服务使用退避。
- 确保重试操作是安全的，或显式实现幂等保护。
- 不要吞掉错误。如果故意忽略某个错误，在适当级别记录并说明原因。
- 让回滚和恢复路径与成功路径一样经过严格测试。

## 9. 安全

- 默认采用最小权限。
- 在访问前规范化和校验路径，并确认解析后的路径仍位于配置的沙箱根目录内。
- 当基于参数的进程 API 足够时，绝不通过不受限的 Shell 执行命令。
- 独立地针对策略校验可执行文件名称和参数。
- 对状态、配置和可进化脚本使用原子写入，避免部分输出不安全的情况。
- 在持久化、记录日志或加入 LLM 提示词之前脱敏机密。
- 将工具输出和 LLM 输出视为不可信输入。
- 在使用点进行授权校验，而不只是在 API 入口。

## 10. 测试

- 为每个行为变更和 bug 修复添加或更新测试。
- 对纯逻辑和聚焦的契约使用单元测试。
- 对模块边界、持久化、沙箱行为、子进程和恢复流程使用集成测试。
- 包含针对非法输入、被拒绝的能力、目录穿越、超时、预算耗尽、畸形响应和回滚失败的负面测试。
- 保持测试确定、隔离，并可在并行下安全运行。
- 默认测试套件不得依赖真实外部服务。使用受控的假件或本地测试服务器。
- 断言可观察的行为和契约，而不是私有实现细节。
- 给测试起描述性名称，说明条件和预期结果。
- 不稳定的测试是缺陷，必须修复或附上明确说明后移除。

## 11. 格式化与静态分析

- 在认为工作完成之前，始终使用 `cargo fmt` 格式化 Rust 代码。
- 运行 `cargo clippy --all-targets --all-features -- -D warnings` 并解决所有警告。
- 使用 `cargo test --all-targets --all-features` 运行完整的相关测试套件。
- 使用项目配置的工具一致地格式化 Markdown、TOML、SQL、JSON、YAML 和 Rhai 文件。
- 不要手动对齐代码，与自动化格式化工具冲突。
- 不要为了回避局部问题而全局抑制 lint。使用最窄的抑制并说明原因。
- 生成的文件必须明确标识，且不得手工编辑。

## 12. 依赖

- 只有在提供标准库或既有依赖无法合理覆盖的明确价值时，才添加依赖。
- 优先使用维护良好、审计充分的 crate，并启用最少必需的特性。
- 当默认特性引入不必要的功能或依赖负担时，禁用它们。
- 通过 `Cargo.lock` 固定依赖，保证可重现的应用构建。
- 在采纳前审查安全公告、许可和传递依赖影响。
- 未经记录理由，不要为同一职责引入多个 crate。

## 13. 配置与兼容性

- 配置用于运维策略，而不是掩盖不完整的行为。
- 提供安全且有用的默认值。
- 在启动时校验配置，并清晰报告所有可操作的校验失败。
- 保持环境变量和命令行覆盖的显式与文档化。
- 将持久化的事件格式、数据库 schema、配置键和脚本接口视为有版本的契约。
- 对破坏性持久化数据变更提供迁移或显式的兼容性错误。

## 14. 变更纪律

- 保持变更聚焦，避免在同一变更集中进行无关重构。
- 除非破坏性变更是有意的且有文档记录，否则保持向后兼容。
- 每当公共行为或配置变化时，更新文档和示例。
- 包含能证明缺陷已修复并防止回归的测试。
- 不要让仓库停留在格式化、静态分析、编译或测试失败的状态。

## 15. 完成定义

只有当所有适用条件都满足时，变更才算完成：

- 实现完整、安全、可投产。
- 添加到仓库的所有文本均为英语。
- 代码遵循预期的模块边界，没有多余公共面。
- 必要的技术注释和公共 API 文档准确且简洁。
- 错误包含可操作的上下文，相关操作可通过安全的结构化日志观测。
- 测试覆盖成功、失败和边界条件。
- 格式化、静态分析、编译和相关测试通过。
- 在需要时更新文档、配置示例和迁移。
- 不残留机密、临时调试输出、占位符、死代码或无关产物。
